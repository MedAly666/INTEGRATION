Définition : Intégration de données
L'intégration de données consiste à fournir un accès uniforme à des sources
multiples autonomes hétérogènes structurées.
Décortiquons la définition...
 un accès : (requêtes, éventuellement mises à jour)
 uniforme : (les sources sont transparentes à l'utilisateur)
 à des sources : (pas seulement des BD)
 multiples : (même 2 est un problème, mais l'objectif final est d'arriver à une
intégration à l'échelle du web : web_scale integration)
 autonomes : (sans affecter le comportement des sources)
 hétérogènes : (différents modèles de données, schémas)
 structurées : (ou au moins semi-structurées)
Remarque : BD intégrée VS BD distribuée
Contrairement aux bases de données distribuées où la distribution est établie d'une
façon organisée et connue, dans l'intégration de données il faut faire face à une
collection de sources préexistantes et une organisation plus complexe et non
forcément bien connue.

Niveau physique (systèmes)
Même dans le cas où le modèle de données des sources est identique (relationnel
par exemple), les différentes implémentations nécessitent un travail de
réconciliation.
Exemple
Des sources relationnelles peuvent être implémentées dans différents SGBD
(Oracle, SQL Server, MySQL...etc). Même si SQL est un standard, il y a des
différences entre ces implémentations (types de données spécifiques,
implémentation des opérateurs 'interrogation...etc).
Niveau social et administratif
L'une des difficultés les plus importantes dans l'intégration des données réside au
niveau administratif. La volonté des propriétaires des données à coopérer est
nécessaire pour la réussite des projets d’intégration.
Pourquoi refuser de coopérer ?
 Les requêtes provenant d'un système d'intégration peuvent constituer une
charge supplémentaire qui alourdirait le système local.
 La peur de remettre en cause la confidentialité de certaines données.
 ...
Remarque
Dans certains cas les raisons du refus de partage de données peuvent être
légitimes, voire même imposées par la loi, par exemple dans le domaine médical.

D. Hétérogénéité des données
L'hétérogénéité concerne les données, les modèles et les langages.
Qu'est ce qu'un système homogène ?
 même logiciel gérant les données sur tous les sites
 même modèle de données
 même univers de discours
Qu'est ce qu'un système hétérogène ?
 n'adhère pas à toutes les caractéristiques d'un système homogène
 langages de programmation et d'interrogation différents, modèles différents,
SGBD différents
le problème de l'hétérogénéité peut concerner deux catégories : [2]
 Hétérogénéité structurelle ou schématique
 Hétérogénéité sémantique
Hétérogénéité structurelle ou schématique
Elle provient quand les sources adoptent différents modèles de données, structures
de données ou schémas, par exemple les modèles de bases de données
relationnelles ou orientées objets. De nombreux travaux concernant ce type
d'hétérogénéité ont été proposés dans les contextes des bases de données fédérées
et des multi-bases de données. [2]
Remarque
 Bases de données fédérées : Plusieurs BD hétérogènes capables
d interopérer via une vue commune (modèle commun)ʼ
 Multibase de données :Plusieurs BD (hétérogènes ou non) capables
d interopérer sans une vue commune (absence de modèle commun)ʼ
Lorsque les schémas à intégrer sont exprimés dans des modèles de données
différents, on parle alors de correspondance d'hétérogénéité des modèles de
données. La traduction de ces schémas dans un modèle pivot permet de résoudre
ce type de conflits.
Hétérogénéité sémantique
Elle est due aux conflits sémantiques dans les termes, les expressions, etc., qui
sont adoptés par différents schémas de données mais exprimés de diverses
manières. Autrement dit, elle est due aux différentes interprétations pour les objets
du monde réel.
En effet, les sources de données ont été conçues indépendamment par des
concepteurs différents ayant des objectifs applicatifs différents. Chacun peut donc
avoir un point de vue différent sur le même concept. [2]
Types de relations sémantiques
 R1 identique à R2 : même constructeur, même concept
 R1 équivalente à R2 : constructeurs différents, même concept
 R1 compatible avec R2 : ni identiques, ni équivalents
 R1 incompatible avec R2 : contradictoires

Conflits de représentation
Ces conflits se trouvent dans le cas où nous utilisons des propriétés différentes ou
des schémas différents pour décrire le même concept. Cela signifie que le nombre
de classes et propriétés et les classes et propriétés représentant un concept C dans
les sources ne sont pas égaux. [2]
Exemple
Pour décrire un disque dur le fournisseur S1 utilise
 2 classes : Composants et DisqueDur
 4 propriétés : situation, fournisseur, prix, et capacité .
Le fournisseur S2 utilise
 une seule classe : HardDisk
 5 propriétés : situation, supplier, price, tax, et capacity.
Exemple
Pour calculer le prix d'un disque :
 S2 utilise deux propriétés : price et tax.
 S1 n'utilise qu'une seule : prix.
Conflits Données/Méta-données,
Il existe des conflits de type données/méta-données lorsqu'une donnée dans un
schéma correspond à une une méta - donnée dans un autre schéma.
Exemple
Article_conférence est une valeur associée à l'attribut type_publication dans un
schéma S1 alors que ce concept est modélisée comme étant un attribut dans un
autre schéma.
Conflits descriptifs
Les conflits descriptifs apparaissent entre concepts possédant des caractéristiques
différentes bien qu'ils soient proches sémantiquement :
 Nommage. Un même nom peut être utilisé pour dénoter deux concepts
différents (problème d'homonymie) ou un même concept est décrit par des
noms différents (problème de synonymie).
 Identité. Un même concept peut être identifié dans deux schémas différents
avec deux identificateurs différents.
 Échelle . Ce type de conflits décrit un même objet qui est représenté par des
unités différentes.
 Conflit de précision.
Exemple
 Nommage : Le même concept de disque dur est nommé par DisqueDur dans
la S1, et par HardDisk dans la S2. La propriété Situation se trouve dans les
deux sources, mais avec deux significations différentes.

Conflits de contexte
Le contexte est une notion très importante dans les systèmes d'information
répartis. En effet, un même objet du monde réel peut être représenté dans les
sources de données par plusieurs représentations selon un contexte local à chaque
source. Ces conflits de contexte se trouvent dans le cas où les concepts semblent
avoir la même signification, mais ils sont évalués dans différents contextes.
Exemple
La propriété prix de disque dur ne s'applique que pour un disque dur neuf dans S1,
mais peut l'être pour tous les disques soit neufs ou d'occasions dans S2.

G. Cadre formel pour l'intégration des données
Un système d'intégration de données est un triplet (G,S,M) où : [14]
 G est un schéma global exprimé à travers un ensemble de prédicats et de de
formules bien formées de la logique du 1er ordre.
 S est le schéma source, composé des schémas d'un ensemble de sources.
Les schémas sources sont des ensembles de symboles de prédicats (ou
relations), d'un alphabet As.
 M est la fonction de mappage entre G et S, c'est un ensemble d'assertions
dans lesquelles les requêtes exprimées sur G sont mises en correspondance
avec les requêtes exprimées en S.

symboles de relations binaires. IsBossOf , IsMemberOf et WorksIn.

Plusieurs classifications des systèmes d'intégration existent dans la littérature , en
fonction des critères de classification choisis. Nous citons trois critères :
 La représentation de données intégrées : virtuelle ou matérialisée,
 Le sens de la mise en correspondance entre schéma global et les schémas
locaux
 La nature du processus d'intégration. [5]
A. Degré de matérialisation
Il existe essentiellement deux principales approches pour intégrer des données
provenant de différentes sources:
 Les systèmes de médiation et les entrepôts de données (architecture
virtuelle).
 Les entrepôts de données (architecture matérialisée).
 Les systèmes de médiation permettent d'accéder par une même requête à
des données se trouvant dans des sources différentes.
 Les entrepôts de données intègrent au sein d'une même base des données
provenant de sources différentes, permettant ainsi d'effectuer des analyses
et des fouilles de données sur la nouvelle base.
1. Architecture matérialisée
Cette architecture consiste à centraliser physiquement, dans un entrepôt de
données, l'ensemble de données consolidées à partir de diverses sources
(catalogues électroniques, bases de données relationnelles, Web, etc.).
15
Principe
L'utilisateur interroge une base de données réelle (l'entrepôt) contenant une copie
des données pertinentes des différentes sources considérées .
Le processus de construction d'un système d'intégration matérialisé se compose en
quatre étapes principales [7]:
 Extraction des données des sources de données,
 Transformation des données au niveau structurel,
 Intégration sémantique des données,
 Stockage des données intégrées dans le système cible.
Ces étapes correspondent aux outils d'ETL (extract, transform and load). Les deux
premières étapes sont habituellement prises en charge par le même composant
logiciel, appelé adaptateur. Chaque adaptateur fournit ainsi une interface d'accès et
de requêtes sur la source. Les données extraites sont ensuite intégrées en
éliminant les conflits, puis stockées dans l'entrepôt.
Remarque
Comme dans l'approche médiateur, l'objectif d'un adaptateur est d'aboutir à des
données représentées dans un même format.
Avantage de la matérialisation
L'interrogation d'un entrepôt de données se fait directement sur les données de
l'entrepôt et non sur les sources originales. Il est donc possible d'utiliser les
techniques d'interrogation et d'optimisation des bases de données traditionnelles.
Inconvénient de la matérialisation
Cette approche exige :
 Un coût de stockage supplémentaire
 Un coût de maintenance causé par les opérations de mises à jour au niveau
de sources de données (toute modification dans les sources locales doit être
répercutée sur l'entrepôt de données).
Pour résumer
Dans les entrepôts de données, les données sont extraites à partir de sources de
données disparates et matérialisées dans l'entrepôt de données. Le principe de la
matérialisation est l'intégration réelle de données conformément au schéma global.

2. Architecture virtuelle
Cette architecture consiste à développer une application chargée de jouer le rôle
d'interface entre les sources de données locales et les applications d'utilisateurs.
Principe
L'utilisateur interroge un médiateur chargé de traduire la requête pour interroger
les différentes sources et de combiner les résultats obtenus.
le principe repose sur deux composants essentiels : [5]
 Le médiateur
 L'adaptateur
Définition : Le médiateur
Est chargé de la localisation des sources de données et des données pertinentes par
rapport à une requête, il résout de manière transparente les conflits de données.
Un ensemble de connaissances sur les sources permet au médiateur de générer un
plan d'exécution pour traiter les requêtes d'utilisateurs. [5]
Définition : L'adaptateur
Est un outil permettant à un (ou plusieurs) médiateur(s) d'accéder au contenu des
sources d'informations dans un langage uniforme. Il fait le lien entre la
représentation locale des informations et leur représentation dans le modèle de
médiation. [5]
Remarque
Dans cette approche, les données ne sont pas stockées au niveau du médiateur.
Elles restent dans les sources de données et ne sont accessibles qu'à ce niveau.
L'intégration d'information est fondée sur l'exploitation de vues abstraites décrivant
de façon homogène et uniforme le contenu des sources d'information dans les
termes du médiateur. Les sources d'information pertinentes, pour répondre à une
requête, sont calculées en fonction de la définition de ces vues.
Le problème consiste à trouver une requête qui est équivalente à la requête de
l'utilisateur.
Les réponses à la requête sont obtenues en évaluant cette requête sur les
extensions des vues. [5]

Remarque
Le problème d'hétérogénéité sémantique entre les différentes sources d'information
ne se pose pas pour l'utilisateur puisqu'il est résolu par le médiateur.
Avantage de l'approche médiateur
Permet de construire un système d'interrogation de sources de données sans

Défis
Dans cette approche, deux problèmes apparaissent : comment construire le
schéma intégré et comment effectuer la mise en correspondance entre les termes
utilisés dans ce schéma et les structures des schémas des sources qui contiennent
les données. [5]
Pour résumer
Un système de médiation est constitué d'un système global de gestion le
médiateur, d'un ensemble d'adaptateurs et d'un ensemble de sources locales. Les
sources locales sont intégrées dans le sens qu'un seul schéma global est construit à
partir des schémas exportés par les sources locales. Des requêtes sont ainsi posées
sur le schéma global et traitées par le médiateur. Les schémas des sources sont
construits par des adaptateurs qui établissent la correspondance entre la source et
le médiateur. [5]
3. Comparaison des deux approches
Approche virtuelle préférable si :
 Les sources sont mises à jour fréquemment.
 Les sources sont très nombreuses.
 Il est impossible de prédire les requêtes de l'utilisateur.

locaux
Un autre critère de classification est le mapping dans l'intégration de données qui
sert à définir la relation entre le modèle global et celui des sources. Plusieurs
approches et systèmes d'intégration ont été proposés dans la littérature :
 Global As View (GAV)
 Local As View (LAV)
 Approches hybrides :
 Generalized-Local-as-View (GLAV)
 Both As View (BAV)
 Both Global
19
Classification des systèmes d'intégration
1. Approche GAV
Dans l'approche GAV , le mapping fait correspondre à chaque concept ConceptG du
schéma global G une vue VueL sur le schéma local.
Dans cette approche, la transformation d'une requête sur le schéma global en
requêtes sur les schémas locaux est une simple opération faite par le gestionnaire
de vues.
Remarque
Dans une architecture GAV, une modification sur les sources locales ou sur leur
schéma entraîne une reconsidération du schéma global.
Concrètement
L'approche GAV consiste à définir à la main (ou de façon semi-automatique) le
schéma global en fonction des schémas des sources de données à intégrer puis à le
connecter aux différentes sources. Pour cela, les prédicats du schéma global, aussi
appelés relations globales, sont définis comme des vues sur les prédicats des
schémas des sources à intégrer. [5]
Comme les requêtes d'un utilisateur s'expriment en termes des prédicats du
schéma global, nous obtenons facilement une requête en termes du schéma des
sources de données intégrées, en remplaçant les prédicats du schéma global par
leurs définitions. [5]
2. Approche LAV
L'approche LAV fait correspondre à chaque concept ConceptL du schéma local une
vue VueG sur le schéma global. Le traitement de la requête exprimée en termes du
schéma global est plus complexe car il se fait par une réécriture en termes de vues,
autrement dit, la requête sur le schéma global doit être reformulée suivant les
schémas des sources locales.

3. Approches d'intégration hybrides
Il y a eu des tentatives de fusionner les approches LAV et GAV de sorte qu'il serait
facile de reformuler la requête, comme c'est le cas dans l'approche GAV, ainsi que
pour modifier les schémas locaux, comme c'est le cas dans l'approche LAV. [5]
a) Approche GLAV
GLAV (Generalized-Local-as-View), se base sur des vues au niveau global et local.
Une correspondance entre les vues au niveau global et local est requise. Ces
correspondances n'ont pas de direction et s'appliquent dans les deux sens. [5]
Dans l'approche GLAV, l'indépendance du schéma global (permet l'ajout et la
suppression de sources), l'adaptation de nouvelles sources et la complexité pour
reformuler des requêtes sont les mêmes que dans l'approche LAV .
b) Approche BAV
Both As View (BAV) est une autre approche d'intégration de données. C'est un
cadre riche d'intégration, qui est basé sur l'utilisation des séquences réversibles des
transformations primitives de schéma, appelé "transformation pathways". [5]
C. Automaticité du processus de mapping
Ce dernier critère permet de distinguer les approches d'intégration selon le degré
d'automaticité du processus d'intégration. Cette automaticité concerne la résolution
ou l'élimination des conflits sémantiques entre les sources durant le processus
d'intégration.

Remarque
En pratique la création du mapping prend > 50% de l'effort d'intégration!
1. Les approches manuelles
Les premières approches proposées étaient des approches manuelles. Ces
approches permettent d'automatiser l'intégration des données au niveau
syntaxique. Les conflits sémantiques sont gérés manuellement et nécessitent la
présence d'un expert humain pour interpréter la sémantique des données. [5]
Remarque
Ces approches manuelles deviennent impraticables lorsque le nombre de sources de
données à intégrer est important, ou lorsque les sources évoluent fréquemment.
2. Approches semi-automatiques
Afin d'apporter plus d'automatisation dans la résolution des conflits sémantiques,
plusieurs travaux se sont tournés vers les ontologies.
Une ontologie permet de fournir la sémantique des concepts d'un domaine de
manière formelle.
Les approches semi-automatiques reposent sur des ontologies linguistiques et
permettent d'automatiser partiellement la gestion des conflits sémantiques.
Remarque
Les ontologies linguistiques traitent des termes, et non des concepts. Ceci peut
créer des conflits de noms.
3. Approches automatiques
Les approches automatiques consistent à associer aux données des sources une
ontologie conceptuelle qui en définit le sens. Une ontologie conceptuelle traite les
concepts d'un domaine donné. Elle est définie comme « une spécification formelle
et explicite d'une conceptualisation partagée d'un domaine de connaissance ».
La sémantique du domaine est ainsi spécifiée formellement à travers des concepts,
leurs propriétés ainsi que les relations entre les concepts. La référence à une
ontologie permet d'éliminer automatiquement les conflits sémantiques entre les
sources.
La connexion entre les sources et les ontologies peut se faire de plusieurs
manières : [5]
 Définition des termes de la BD par les concepts ontologiques
 Annotation des données
 Enrichissement de la source par des règles logiques (logique de description)

A. Concepts de base
L'architecture de médiation fut conçue en 1992 par Gio Wiederhold dans l'article
fondateur «Mediator in the architecture of future information systems» [9]. Il y
développe une nouvelle vision de l'architecture du traitement de l'information en
entreprise, il tente de régler la problématique de l'accès et de l'intégration de
l'information en introduisant la notion de médiateur.
Cette architecture est basée sur deux concepts fondamentaux :
 Médiateurs (Mediators)
 Adaptateurs (Wrappers)
Définition : Médiateur
C' est un module logiciel recevant directement la requête d'un utilisateur et devant
la traiter. Celui-ci doit localiser l'information nécessaire pour répondre à la requête,
résoudre les conflits schématiques et sémantiques, interroger les différentes
sources et intégrer les résultats partiels dans une réponse homogène et cohérente.
Définition : Adaptateur (Wrapper)
Il s'agit ici d'un composant logiciel qui permet à un système local de distribuer ses
informations à une collectivité d'usagers. L'adaptateur permet de présenter les
données dans le format syntaxique de la médiation.
C'est donc une interface permettant l'interrogation d'une base de données grâce à
un langage normalisé (langage pivot).

2. Adaptateurs
Adaptateur (Wrapper)
Un adaptateur prend en compte les dimensions Distribution, Autonomie et
Interopérabilité. Son objectif est d'accéder à une source, d'extraire les données
appropriées et de les présenter dans un format spécifié.
Un adaptateur est donc un composant qui :
 Réalise la transformation entre le modèle de données dans lequel sont
représentées les données de la source et le modèle choisi au niveau
médiateur.
 Effectue la transformation entre les expressions de requêtes du niveau
global en expressions compréhensibles par les sources. Inversement, il
traduit les réponses des sources au format du niveau global.
 Assure les traitements spécifiques non disponibles au niveau local et
nécessaires pour le niveau global (augmentation du pouvoir d'expression et
de traitement de la source locale).
Exemple
Caractéristiques d'un adaptateur
 Traduit le schéma des sources en termes du schéma global.
 Traduit les requêtes du médiateur en termes compréhensibles par les
sources.
 Traduit les résultats renvoyés par la source en termes du schéma global.
Remarque : Les adaptateurs sont également :
 Assez difficiles à écrire.
 Éventuellement « intelligent » : effectuer des optimisations spécifiques aux
sources.
 Généralement associés aux sources, mais peuvent aussi se trouver dans le
médiateur.
Remarque
Le besoin d'avoir un adaptateur par source peut constituer un obstacle à
l'intégration d'un nombre important de sources.

Pré-intégration
Choix de la stratégie du processus d'intégration, ce qui guide le choix des schémas
à intégrer.
Comparaison des schémas.
Les schémas sont analysés et comparés afin de déterminer les correspondances
entre concepts et détecter les conflits.
Mise en conformité des schémas.
Une fois les conflits détectés, on s'efforce de les résoudre pour que la fusion de
divers schémas soit possible.
La résolution automatique des conflits n'est généralement pas réalisable car
l'interaction avec les concepteurs est nécessaire.
Fusion et Restructuration.
Les schémas sont prêts à être superposés, donnant lieu à un ou plusieurs schéma
(s) intermédiaire (s) intégré (s).
Les résultats intermédiaires sont analysés et, si nécessaire, restructurés afin
d'atteindre les critères suivant :
 Exhaustivité et exactitude.
 Minimalité.
 Compréhensibilité.
Exhaustivité et exactitude
Le schéma intégré doit contenir tous les concepts apparaissant correctement dans
n'importe quel schéma de composant.
Minimalité
Pas de redondance dans le schéma intégré.
Compréhensibilité
Le schéma intégré doit être facile à comprendre pour le concepteur et les
utilisateurs finaux.

B. Reformulation de requêtes
Un utilisateur du système d'intégration de données pose des requêtes en termes du
45
schéma de médiation, plutôt que directement dans le schéma où résident les
données.
En conséquence, un système d'intégration de données doit d'abord reformuler une
requête utilisateur dans une requête qui fait référence directement aux schémas
dans les sources.
Les inputs de la reformulation
 Une requête Q posée sur le schéma de médiation
 Descriptions des sources de données
Les résultats de la reformulation
Une requête Q' sur les relations des sources de données, tel que:
 Q' ne fournit que des réponses correctes à Q, et
 Q' fournit toutes les réponses possibles de Q en fonction des sources.
Remarque
Pour effectuer l'étape de reformulation, le système d'intégration de données utilise
les descriptions des sources.
Les catalogues contiennent des descriptions suivantes :
 Le contenu logique des sources
 Les capacités des sources
 La complétude des sources
 Les propriétés physiques des sources et du réseau
 Les statistiques sur les données
 La fiabilité des sources
 Les sources miroirs
Exemple : Éléments de la description des sources
 Contenu : la source contient des films, leurs réalisateurs, ...
 Contraintes : tous les films produits après 1965.
 Complétude : la source contient tous les films américains,
 Capacités : la source doit recevoir le titre du film ou le directeur comme
entrée, la source peut effectuer des sélections.
Deux approches duales
GAV : Global as View
 Schéma global défini comme une vue intégrante sur schémas locaux
 Approche ascendante depuis les sources vers le médiateur
 Difficulté pour ajouter une source
LAV : Local As View
 Chaque source locale est définie comme une vue locale du schéma global
 Approche descendante depuis le médiateur vers les sources
 Difficulté pour réconcilier source et vue locale

3. GaV vs LaV
Global as View
 + La réécriture d'une requête est simple : dépliage
 + Conception naturelle et intuitive
 - Évolution difficile (l'ajout d'une source est compliqué et nécessite de
reconstruire le schéma global)
 - nombre de sources limité (passage à l'échelle difficile)
Local as View
 + Très souple. On dispose de toute la puissance du langage de requêtes
pour définir le contenu des sources.
 + Chaque source est décrite de façon isolée
 + Évolution facile : ajouter une source = écriture d'une requête, pas d'effet
sur le schéma global
 + Le contenu des sources est bien spécifié (spécifier des conditions dans la
requête)
 - La reformulation des requêtes est complexe (réécriture en termes de vues)

Requêtes conjonctives
Dans un système d'intégration, l'interrogation s'effectue généralement en utilisant
des requêtes conjonctives à base de règles définies à l'aide du vocabulaire du
schéma global qui exprime les vues sur les différentes sources.
Une requête conjonctive a la forme d'une règle se présentant comme suit :
 q , et r1,....rn sont des noms de

Dans cette notation, les prédicats de jointure de SQL sont exprimés par les
occurrences multiples de la même variable dans différents subgoals du corps

Inclusion et équivalence
Les notions d'inclusion et d'équivalence de requêtes, permettent la comparaison
entre les différentes reformulations de requêtes.
Elles seront utilisées lors du test de la justesse d'une réécriture d'une requête en
termes d'un ensemble de vues. Dans les définitions qui suivent, nous supposons
que les réponses aux requêtes sont des ensembles de tuples.

Définition : Inclusion et équivalence de requêtes
Une requête Q1 est dite incluse dans une requête Q2, si pour une base de données
D , l'ensemble des tuples calculé pour Q1 est un sous ensemble de l'ensemble des
tuples calculé pour Q2.
Les deux requêtes sont dites équivalentes si Q1 est incluse dans Q2 et Q2 est
incluse dans Q1.
b) Algorithme "Bucket"
L'algorithme Bucket a été développé dans le cadre du système Information
Manifold. Son idée principale, est la suivante : le nombre de réécritures qui ont
besoin d'être considérées, peut être extrêmement réduit si nous considérons
chaque subgoal en isolation, et nous déterminons quelles vues peuvent être
pertinentes pour chaque subgoal. [15]
Algorithme Bucket
 Input : Une Requête conjonctive R, et un ensembles de vues, V1,...Vn
 Output :un ensemble de réécritures de Q en terme d'un sous ensemble des
vues V1,...,Vn
Étapes de l'algorithme
 Étape 1 : Pour chaque sous-requête de R (à part les prédicats de
comparaison), créer un bucket (seau) comprenant les vues (sources)
pertinentes pour la sous requête.
 Étape 2 : Union de toutes les combinaisons valides des sources avec
élimination des redondances
Étape 1
Créer un bucket ("seau") pour chaque subgoal de Q qui ne figure pas dans les
subgoals des prédicats de comparaison. Ce bucket contient les vues qui sont
pertinentes pour répondre au subgoal particulier.
D'une façon générale, une vue V est mise dans un bucket d'un subgoal g de la
requête si la définition de V contient un subgoal g1 tel que : [15]
 g et g1 peuvent être unifiés, et
 après l'application de l'unification à la requête et aux variables de la vue qui
apparaissent dans l'entête, les prédicats dans Q et dans V sont
mutuellement satisfiables
Étape 2
L'algorithme considère des réécritures de la requête qui sont des requêtes
conjonctives.
Il calcule le produit cartésien de tous les buckets et élimine les combinaisons qui ne
satisfont pas la requête, et celles qui sont redondantes.

D. Optimisation
Un système de base de données relationnelle traditionnel accepte une requête
déclarative en SQL. Le système analyse d'abord la requête avant de la transmettre
à l'optimiseur de requêtes.
L'optimiseur produit un plan d'exécution de requête efficace pour la requête, qui est
un programme impératif qui spécifie exactement comment évaluer la requête.
En particulier, le plan spécifie l'ordre d'exécution des opérations de la requête
(jointure, sélection et projection), la méthode de mise en œuvre de chaque
opération (telle que la jointure par tri ou par hachage) et l'ordonnancement des
différents opérateurs (où le parallélisme est possible).

En général, l'optimiseur sélectionne un plan d'exécution de requêtes en recherchant

Pour évaluer le coût d'un plan d'exécution de requête, l'optimiseur s'appuie sur des

 La taille des relations,
 La taille des domaines
 La sélectivité des prédicats.
Enfin, le plan d'exécution des requêtes passe au moteur d'exécution de requêtes,
qui évalue la requête.
Le cas des bases de données traditionnelles diffère de celui de l'intégration des
données.
Dans le contexte d'intégration, l'optimiseur a peu d'informations sur les données,
car les données se trouvent dans des sources autonomes distantes plutôt que
localement.
De plus, comme les sources de données ne sont pas nécessairement des systèmes
de base de données, les sources peuvent avoir des capacités de traitement
différentes.
Exemple
Une source de données peut être une interface Web pour un système d'information
classique, tandis qu'une autre peut être un programme qui analyse des données
stockées dans un fichier structuré.
Remarque
Les optimiseurs de requêtes dans les systèmes de base de données distribués
tiennent compte également où les parties de la requête sont exécutées, mais dans
ce contexte, les différents processeurs ont des capacités identiques.
Enfin, comme les données doivent être transférées sur un réseau, l'optimiseur de
requêtes et le moteur d'exécution doivent pouvoir s'adapter aux délais de transfert
de données.

1. Modèles de coût
Un modèle de coût permet d'estimer le coût que prendra un plan d'exécution, en
s’appuyant sur les statistiques et des formules de coûts, dan le but de choisir parmi
tous les plans d'exécution celui de coût minimal pour l'exécution.
Quelles statistiques
 Du système : Système d'exploitation (CPU, E/S), SGBD (taille d'une page,
taille cache)
 Des données : cardinalité d'une collection, sélectivité d'un attribut, etc.
Modèle de coût pour un médiateur
Coût d'exécution d'une requête = coût de communication + opérations du
médiateur + coûts sur les adaptateurs + congestion du réseau
 Coût de communication : Dépend du débit et de la taille des données
 Opérations du médiateur : Formule classique de coût de calcul d'opérateurs
en mémoire
 Coûts sur les adaptateurs : coûts_fils inclus dans [max
(coût_filsi),Σ(coût_filsi)] suivant degré de parallélisme.
 Congestion du réseau : Difficile à gérer : latence et temps d'attente au
moment de l'exécution de la requête .
Coût des adaptateurs
Les sources sont indépendantes et ne communiquent pas forcément leurs
informations de coûts.
Différentes stratégies permettant d'estimer le coût d'une requête sur une source
 Estimation analytique (Soumission de formules)
 Apprentissage progressif (Gestion d'historique)

A. Problème de la réconciliation
Le problème de réconciliation de références a été étudié dans une multitude de
domaines et sous différentes terminologies. [6]
 Dans le domaine d'Intégration de Données, lors de la fusion de plusieurs
bases ou de leur nettoyage, on cherche à détecter les enregistrements qui
se réfèrent à la même entité du monde réel ; on parle alors d'appariement
de données, de merge/purge et de détection de doublons.
 Dans le domaine du Traitement Automatique du Langage Naturel, lorsqu'on
souhaite trouver quels sont les groupes nominaux qui se réfèrent à la même
entité, on parle de co-référence et de résolution des anaphores.
 En Traitement d'Images, la recherche de correspondances d'objets permet
de détecter que deux régions dans deux images différentes représentent le
même objet.
Remarque
Le problème réconciliation de références est étudiés dans différents travaux sous
différentes appellations parmi lesquelles :
 Résolution d'entités
 Détection de doubles
 Appariement d'entités
Dans les approches traditionnelles, pour décider de la réconciliation de paires de
références, on mesure leur similarité en se fondant uniquement sur leur description
syntaxique structurée (ou non) en attributs. Dans ce cas, on parlera alors
d'approches locales. [6]
Remarque
Une mesure de similarité est une fonction qui calcule le degrés de rapprochement
entre deux entités.
59
Des travaux plus récents ont souligné le fait que la plupart des décisions de
réconciliation et de non réconciliation doivent être effectuées de manière
dépendantes les unes des autres. En effet, des informations relationnelles sont
souvent représentées dans les données. Il s'agit alors d'approches de réconciliation
de références dites globales où l'on exploite à la fois la similarité des valeurs des
attributs mais aussi celles des références reliées par des relations.
Exemple
Par exemple, la peinture "La Joconde" est présentée au musée du "Louvre" et elle a
été réalisée par le peintre "Leonardo Da Vinci". Afin d'améliorer la qualité des
résultats de la réconciliation de références, ces informations relationnelles peuvent
être exploitées et ainsi compléter les informations prises en compte pour les
décisions de réconciliation des références.
Pour réconcilier deux titres de peintures (par exemple "La Joconde" et "jocande"),
on exploite la similarité des musées où elles sont présentées et la similarité de leur
peintre ; pour réconcilier deux musées, on exploite la similarité des peintures qui y
sont présentées, de leur villes de localisation, et ainsi de suite.
Remarque
Cette interdépendance des décisions rend la tâche de réconciliation plus complexe.
D'une part, les tâches élémentaires (e.g. calcul de similarité) deviennent plus
coûteuses et d'autre part, elles doivent être itérées pour prendre en compte
l'interdépendance entre réconciliations. [6]
Le développement de nouvelles techniques de classification en apprentissage
automatique et en statistique a conduit à l'apparition de nouvelles techniques de
réconciliation de références fondées sur l'apprentissage automatique supervisé ou
semi-supervisé. Ces techniques exploitent des échantillons de données sous la
forme d'un ensemble de paires de références étiquetées manuellement par un
expert comme réconciliées ou non réconciliées.6 [6]

a) Méthodes locales de réconciliation de références
Les méthodes locales de réconciliation de références sont des méthodes qui
exploitent les descriptions syntaxiques des références.
Ces méthodes considèrent les descriptions des références représentées en terme
d'ensemble de couples (attribut, valeur).

Exemple

 desc(m1) = {(Nom,"Arts Premiers"), (Adresse,"27, quai Branly 75007

Pour pouvoir décider de la réconciliation (ou non) d'une paire de références, les
méthodes locales de réconciliation comparent les valeurs des attributs deux à deux
afin de capturer la similitude ou la différence des valeurs des attributs décrivant la
paire de références.
Exemple
Pour réconcilier la paire de références m1 et m2, on compare les paires de valeurs
de leurs attributs : ("Arts Premiers", "Musée Quai Branly"), ("27, quai Branly 75007
Paris", "27, quai Branly 7ème arr. Paris"), etc.
Les méthodes s'appuient généralement sur des mesures de similarité appliquées
aux attributs ce qui donne un vecteur de comparaison représentant le score de
similarité ou la probabilité concordance des attributs deux à deux.
Différentes méthodes peuvent être utilisées pour décider de la réconciliation ou non
des paires de références.
 Certaines méthodes s'appuient sur un modèle probabiliste pour estimer les
probabilités de réconciliation et sur des règles de décision appliquées sur ces
probabilités.
 D'autres méthodes exploitent des fonctions d'agrégation de ces similarités
(e.g. moyenne, moyenne pondérée, calcul de rangs).
b) Méthodes globales de réconciliation de références
Les approches locales présentées, considèrent chaque référence comme une entité
complètement indépendante des autres entités et ignorent le fait que les données
sont souvent représentées dans des schémas qui permettent d'exprimer des
relations entre les données.
Exemple
Dans une base de données relationnelle, les données sont stockées dans différentes
tables liées par des relations (clé-étrangères).
De même des données décrites en RDF forment un graphe où les ressources (URIs)
sont reliées entre elles.
Des approches récentes de réconciliation de références exploitent la description des
références en terme d'attributs, mais également les relations liant les différentes
références afin de décider de leur réconciliation.
Exemple
Lorsqu'on cherche à réconcilier "Le Musée du Louvre" avec "Le Louvre", on est
encore plus sûr de leur réconciliation s'ils contiennent tous les deux la peinture "La
Joconde" et si celle-ci a été réalisée par le même peintre "Leonardo Da Vinci".

L'exploitation des relations entre références permet aux méthodes de réconciliation
de réduire à la fois le nombre de fausses réconciliations (Faux Positifs) mais aussi le
nombre de fausses non réconciliations (Faux Négatifs).
Parmi ces méthodes globales nous en distinguons deux types :
 Méthodes globales non itératives de réconciliation de références.
 Méthodes globales itératives de réconciliation de références.
i Méthodes globales non itératives de réconciliation de
références
Il s'agit des approches de réconciliation de références qui exploitent les relations
entre les références et où le calcul est fait une seule fois pour une paire de
références.
En d'autres termes, aucune mise à jour n'est effectuée sur les scores de similarité
(ou probabilité de (non) réconciliation) ni sur les décisions de (non) réconciliation
une fois que ce calcul est réalisé.
ii Méthodes globales itératives de réconciliation de
références
Il s'agit des approches de réconciliation de références qui exploitent les relations
entre les références de manière itérative, en parcourant plusieurs fois les
références.
Toute modification concernant les scores de similarité (ou les probabilités) et
concernant les décisions de (non) réconciliation, est propagée à d'autres
références.
Ceci est itéré jusqu'à ce qu'un point fixe soit atteint : il n'y a alors plus de mise à
jour possible des scores de similarité et/ou plus aucune décision de (non)
réconciliation ne peut être inférée.

 Méthodes déclaratives de réconciliation de références.

des algorithmes d'apprentissage supervisé pour apprendre des connaissances ou
des paramètres nécessaires pour la prise de décision de (non) réconciliation.
Ces connaissances peuvent correspondre soit à des paramètres de mesures de

algorithmes supervisés pour apprendre les connaissances nécessaires à la

C. Mesures de similarité
Une des difficultés les plus importantes auxquelles sont confrontées les méthodes
de réconciliation est la variation syntaxique du vocabulaire utilisé pour décrire les
données.
Ces variations peuvent être dues à différentes raisons :
 Erreurs de saisie
 Abréviations (e.g. bd. pour boulevard),
 Présence d'acronymes (e.g. JSK pour Jeunesse Sportive de Kabylie),
 Synonymes.

2. Mesures fondées sur les chaînes atomiques
Les mesures fondées sur les caractères sont efficaces pour le traitement des
erreurs typographiques. Cependant, il arrive souvent que les différences
typographiques entre les chaînes de caractères soient dues à l'ordre d'apparition
des mots (e.g. "Prof. Marie-Christine Rousset" vs "Rousset Marie-Christine Prof.").
Les mesures fondées sur les caractères sont incapables de capturer la similarité de
telles chaînes de caractères.
Afin de tenir compte de ce type de problèmes, des mesures appliquées sur des
ensembles de chaînes atomiques ont été proposées. [6]
Définition
Une chaîne atomique (ou token) est une séquence de caractères alphanumériques
délimitée par un caractère de ponctuation. Il s'agit en général des mots formant la
chaîne de caractères. [6]

simplement le rapport entre le cardinal de l'ensemble des mots communs entre les
deux chaînes et le cardinal de l'union des mots des deux chaînes :
