B. Reformulation de requêtes
Un utilisateur du système d'intégration de données pose des requêtes en termes du
45
schéma de médiation, plutôt que directement dans le schéma où résident les
données.
En conséquence, un système d'intégration de données doit d'abord reformuler une
requête utilisateur dans une requête qui fait référence directement aux schémas
dans les sources.
Les inputs de la reformulation
 Une requête Q posée sur le schéma de médiation
 Descriptions des sources de données
Les résultats de la reformulation
Une requête Q' sur les relations des sources de données, tel que:
 Q' ne fournit que des réponses correctes à Q, et
 Q' fournit toutes les réponses possibles de Q en fonction des sources.
Remarque
Pour effectuer l'étape de reformulation, le système d'intégration de données utilise
les descriptions des sources.
Les catalogues contiennent des descriptions suivantes :
 Le contenu logique des sources
 Les capacités des sources
 La complétude des sources
 Les propriétés physiques des sources et du réseau
 Les statistiques sur les données
 La fiabilité des sources
 Les sources miroirs
Exemple : Éléments de la description des sources
 Contenu : la source contient des films, leurs réalisateurs, ...
 Contraintes : tous les films produits après 1965.
 Complétude : la source contient tous les films américains,
 Capacités : la source doit recevoir le titre du film ou le directeur comme
entrée, la source peut effectuer des sélections.
Deux approches duales
GAV : Global as View
 Schéma global défini comme une vue intégrante sur schémas locaux
 Approche ascendante depuis les sources vers le médiateur
 Difficulté pour ajouter une source
LAV : Local As View
 Chaque source locale est définie comme une vue locale du schéma global
 Approche descendante depuis le médiateur vers les sources
 Difficulté pour réconcilier source et vue locale

3. GaV vs LaV
Global as View
 + La réécriture d'une requête est simple : dépliage
 + Conception naturelle et intuitive
 - Évolution difficile (l'ajout d'une source est compliqué et nécessite de
reconstruire le schéma global)
 - nombre de sources limité (passage à l'échelle difficile)
Local as View
 + Très souple. On dispose de toute la puissance du langage de requêtes
pour définir le contenu des sources.
 + Chaque source est décrite de façon isolée
 + Évolution facile : ajouter une source = écriture d'une requête, pas d'effet
sur le schéma global
 + Le contenu des sources est bien spécifié (spécifier des conditions dans la
requête)
 - La reformulation des requêtes est complexe (réécriture en termes de vues)
4. Algorithmes de réécriture
Les requêtes et les sources sont écrites sous forme de requêtes conjonctives. A
priori, le nombre de réécritures possibles de la requête en fonction des vues est
exponentiel par rapport à la taille de la requête.
Principe des algorithmes
Réduire le nombre de possibilités en considérant les sous-requêtes (buts partiels) et
en déterminant quelles vues sont pertinentes pour répondre à ces sous requêtes
Conceptuellement : on dispose d'un ensemble de requêtes pré-calculées (les
sources) et on souhaite les utiliser pour répondre aux requêtes.

a) Concepts élémentaires
Requêtes conjonctives
Dans un système d'intégration, l'interrogation s'effectue généralement en utilisant
des requêtes conjonctives à base de règles définies à l'aide du vocabulaire du
schéma global qui exprime les vues sur les différentes sources.
Une requête conjonctive a la forme d'une règle se présentant comme suit :
 q , et r1,....rn sont des noms de
prédicats
 Les prédicats r1(X1),...rn(Xn) sont les subgoals (sous requêtes) du corps de
la requête.
Remarque
Dans cette notation, les prédicats de jointure de SQL sont exprimés par les
occurrences multiples de la même variable dans différents subgoals du corps
Exemple : Requête : Quelles sont les acteurs (nom) dirigés par le
réalisateur James Cameron
Film (titre, année, genre, réalisateur)
Acteur (nom, titre)
Requête conjonctive : Q(n) :- Acteur(n, t), Film(t, a, g, r), r='James Cameron'
Inclusion et équivalence
Les notions d'inclusion et d'équivalence de requêtes, permettent la comparaison
entre les différentes reformulations de requêtes.
Elles seront utilisées lors du test de la justesse d'une réécriture d'une requête en
termes d'un ensemble de vues. Dans les définitions qui suivent, nous supposons
que les réponses aux requêtes sont des ensembles de tuples.

Définition : Inclusion et équivalence de requêtes
Une requête Q1 est dite incluse dans une requête Q2, si pour une base de données
D , l'ensemble des tuples calculé pour Q1 est un sous ensemble de l'ensemble des
tuples calculé pour Q2.
Les deux requêtes sont dites équivalentes si Q1 est incluse dans Q2 et Q2 est
incluse dans Q1.
b) Algorithme "Bucket"
L'algorithme Bucket a été développé dans le cadre du système Information
Manifold. Son idée principale, est la suivante : le nombre de réécritures qui ont
besoin d'être considérées, peut être extrêmement réduit si nous considérons
chaque subgoal en isolation, et nous déterminons quelles vues peuvent être
pertinentes pour chaque subgoal. [15]
Algorithme Bucket
 Input : Une Requête conjonctive R, et un ensembles de vues, V1,...Vn
 Output :un ensemble de réécritures de Q en terme d'un sous ensemble des
vues V1,...,Vn
Étapes de l'algorithme
 Étape 1 : Pour chaque sous-requête de R (à part les prédicats de
comparaison), créer un bucket (seau) comprenant les vues (sources)
pertinentes pour la sous requête.
 Étape 2 : Union de toutes les combinaisons valides des sources avec
élimination des redondances
Étape 1
Créer un bucket ("seau") pour chaque subgoal de Q qui ne figure pas dans les
subgoals des prédicats de comparaison. Ce bucket contient les vues qui sont
pertinentes pour répondre au subgoal particulier.
D'une façon générale, une vue V est mise dans un bucket d'un subgoal g de la
requête si la définition de V contient un subgoal g1 tel que : [15]
 g et g1 peuvent être unifiés, et
 après l'application de l'unification à la requête et aux variables de la vue qui
apparaissent dans l'entête, les prédicats dans Q et dans V sont
mutuellement satisfiables
Étape 2
L'algorithme considère des réécritures de la requête qui sont des requêtes
conjonctives.
Il calcule le produit cartésien de tous les buckets et élimine les combinaisons qui ne
satisfont pas la requête, et celles qui sont redondantes.
Exemple : Source Globale S
 Enrolled(student, dept)
 Registered(student, course, year)
 Course(course, number)

D. Optimisation
Un système de base de données relationnelle traditionnel accepte une requête
déclarative en SQL. Le système analyse d'abord la requête avant de la transmettre
à l'optimiseur de requêtes.
L'optimiseur produit un plan d'exécution de requête efficace pour la requête, qui est
un programme impératif qui spécifie exactement comment évaluer la requête.
En particulier, le plan spécifie l'ordre d'exécution des opérations de la requête
(jointure, sélection et projection), la méthode de mise en œuvre de chaque
opération (telle que la jointure par tri ou par hachage) et l'ordonnancement des
différents opérateurs (où le parallélisme est possible).

En général, l'optimiseur sélectionne un plan d'exécution de requêtes en recherchant
un espace de plans possibles et en comparant leurs coûts estimés.
Pour évaluer le coût d'un plan d'exécution de requête, l'optimiseur s'appuie sur des
statistiques étendues sur les données sous-jacentes, telles que
 La taille des relations,
 La taille des domaines
 La sélectivité des prédicats.
Enfin, le plan d'exécution des requêtes passe au moteur d'exécution de requêtes,
qui évalue la requête.
Le cas des bases de données traditionnelles diffère de celui de l'intégration des
données.
Dans le contexte d'intégration, l'optimiseur a peu d'informations sur les données,
car les données se trouvent dans des sources autonomes distantes plutôt que
localement.
De plus, comme les sources de données ne sont pas nécessairement des systèmes
de base de données, les sources peuvent avoir des capacités de traitement
différentes.
Exemple
Une source de données peut être une interface Web pour un système d'information
classique, tandis qu'une autre peut être un programme qui analyse des données
stockées dans un fichier structuré.
Remarque
Les optimiseurs de requêtes dans les systèmes de base de données distribués
tiennent compte également où les parties de la requête sont exécutées, mais dans
ce contexte, les différents processeurs ont des capacités identiques.
Enfin, comme les données doivent être transférées sur un réseau, l'optimiseur de
requêtes et le moteur d'exécution doivent pouvoir s'adapter aux délais de transfert
de données.

1. Modèles de coût
Un modèle de coût permet d'estimer le coût que prendra un plan d'exécution, en
s’appuyant sur les statistiques et des formules de coûts, dan le but de choisir parmi
tous les plans d'exécution celui de coût minimal pour l'exécution.
Quelles statistiques
 Du système : Système d'exploitation (CPU, E/S), SGBD (taille d'une page,
taille cache)
 Des données : cardinalité d'une collection, sélectivité d'un attribut, etc.
Modèle de coût pour un médiateur
Coût d'exécution d'une requête = coût de communication + opérations du
médiateur + coûts sur les adaptateurs + congestion du réseau
 Coût de communication : Dépend du débit et de la taille des données
 Opérations du médiateur : Formule classique de coût de calcul d'opérateurs
en mémoire
 Coûts sur les adaptateurs : coûts_fils inclus dans [max
(coût_filsi),Σ(coût_filsi)] suivant degré de parallélisme.
 Congestion du réseau : Difficile à gérer : latence et temps d'attente au
moment de l'exécution de la requête .
Coût des adaptateurs
Les sources sont indépendantes et ne communiquent pas forcément leurs
informations de coûts.
Différentes stratégies permettant d'estimer le coût d'une requête sur une source
 Estimation analytique (Soumission de formules)
 Apprentissage progressif (Gestion d'historique)
